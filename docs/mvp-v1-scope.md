# LunaAgentOS 第一版最小需求路径

## 第一版的真正目标

LunaAgentOS 第一版的目标不是“把产品做完”，而是做出一个**可信、可见、可参与**的起点。

这意味着第一版必须同时满足三件事：

1. 证明方向成立
2. 证明协议可跑
3. 证明别人现在加入就有明确位置

## 第一版一句话定义

做出一个真正的桌面控制台原型，至少稳定接通一个现实 Agent 目标，完整展示统一状态流，并让贡献者一眼看懂项目方向、边界和可参与模块。

## P0：必须有

### 1. 项目定位清晰

必须让参与者一眼明白：

- LunaAgentOS 是“现成 Agent 之上的统一控制层”
- 不是又一个聊天器
- 不是另一个单 Agent 套壳
- 不是只做 prompt 工程

### 2. 中文优先的项目入口

至少具备：

- `README.md`
- `README_CN.md`
- 中文优先的项目说明

### 3. 技术路线明确

必须有一份正式技术决策，说明：

- 为什么当前 Python 只是协议验证工具
- 为什么长期主路线倾向 `Tauri 2 + Rust Core`
- 为什么保留 `Avalonia + C#` 作为高质量备选

### 4. 协议骨架已经跑通

必须具备：

- `manifest`
- 生命周期状态机
- 统一消息格式
- `stdio_json / stdio_text` 适配主链

### 5. 一次完整任务闭环

第一版必须能演示：

1. 启动 Agent
2. 发送 prompt
3. 进入 `THINK`
4. 进入 `TOOLING`
5. 输出 `RESP`
6. 收敛到 `DONE`

### 6. 至少一个现实接入目标

第一版不要求同时深接三家，但至少要：

- 真实接入目标清晰
- 首个现实对象优先 `Hermes`
- 第二目标是 `Claude Code`
- `Trae IDE` 作为桥接位，不伪装成当前 CLI Adapter 已原生接通

### 7. 最小桌面控制台原型

哪怕很简，也要开始体现“控制台”而不是脚本：

- Agent 列表
- 当前输出区
- 状态 / 工具区
- 人类输入入口

### 8. 可参与的模块边界

必须让别人知道能从哪里开始接：

- Adapter 协议层
- Runtime / Process 层
- Desktop Shell
- UI 交互层
- 具体 Agent 接入
- Trae Bridge
- 文档 / 测试 / 协议回归

## P1：应该有

### 1. 系统架构图

让参与者一眼理解：

- Core 做什么
- Desktop Shell 做什么
- UI 做什么
- Adapter / Plugin 做什么

### 2. 贡献指南

至少说明：

- 适合贡献什么
- 现在最缺什么
- 提交风格和协作预期

### 3. 路线图

让参与者知道：

- 当前 Phase 0 做什么
- 后续 Phase 1 / 2 怎么扩

### 4. 开放问题清单

明确告诉参与者哪些设计还没锁死，欢迎加入讨论。

## 暂时不要做

第一版不应该过早做这些：

- 一次性深接很多 Agent
- 大而全 GUI
- 复杂权限系统
- 插件市场
- 商业化功能实装
- 为了“好看”而过度设计界面

## 第一版最重要的验收标准

如果一个新参与者打开仓库后，能在 10 分钟内得到这 5 个判断，第一版就算成功：

1. 我知道 LunaAgentOS 是什么
2. 我知道它为什么值得做
3. 我看到它已经不是空想
4. 我知道现在最小能跑到哪一步
5. 我知道自己可以从哪里开始贡献

## 对当前仓库的直接要求

第一版文档和工程应围绕以下资产组织：

- 协议 POC
- 真实接入路线
- 技术选型决策
- 架构说明
- 贡献入口

## 当前建议顺序

1. 保持协议与验证链稳定
2. 做出最小桌面壳方向
3. 优先接 `Hermes`
4. 再推进 `Claude Code`
5. 为 `Trae IDE` 形成桥接方案，而不是假接入
