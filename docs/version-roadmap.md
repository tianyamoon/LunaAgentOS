# 内部推进路线

## 总体判断

LunaAgentOS 的推进不应该按“功能越多越好”来走，而应该按“先拿到真实产品价值，再逐层外扩”来走。

当前最稳的内部推进节奏是：

- `Stage 1`：拿到最小异构雏形
- `Stage 2`：跑通调用流
- `Stage 3`：长成更完整的协作工作台
- `Stage 4`：长成控制平面

说明：

- 这是**内部推进阶段**
- 不是对外发布版本号

## Stage 1：最小异构雏形

### 目标

让 LunaAgentOS 至少真实接入两种不同类型的入口，并形成最小可用的异构桌面工作台。

### 核心能力

- 左侧入口舰队
- 主 agent 设定
- 中间主 agent 多会话卡片
- 卡片展示输出流 / 思考流 / 最终响应
- 右侧历史任务
- 历史按日期 JSON 存储
- `Claude Code` 真实可用
- `Hermes` 真实可用
- 启动轻、静默、不打断用户

### 产品价值

这一版的价值不只是替代 Claude CLI 入口，而是先证明：

- LunaAgentOS 不是单一 Agent 壳
- 它已经具备“强大入口 + 通用入口”的最小异构控制台雏形

### 关键边界

- `Claude Code` 在 `v1` 中按“单入口 + 多会话”建模
- Claude 内部 subagent / delegation 仍视为其内部机制
- 这些内部对象不提升为 LunaAgentOS 左侧独立 agent
- `v1` 管理的是外部入口与 session，不是 Claude 内部 worker

## Stage 2：跑通调用流

### 目标

让会话中的内容可以被转发给其它入口或其它 session，开始形成可见协作流。

### 核心能力

- 用户可以选中会话中的一段内容并转发给其它目标
- 目标可以是另一个入口，也可以是既有 session
- 转发链路可见
- 多卡片协作可见
- 为后续 agent 主动 `@` 其它 agent 的协作方式打基础

### 产品价值

这一版意味着 LunaAgentOS 从“多入口工作台”开始进入“可协作工作台”。

## Stage 3：更完整的协作工作台

### 目标

从“人手动转发”升级到“系统理解关系、agent 能主动协作”的工作台。

### 核心能力

- agent 主动 `@` 其它 agent，由系统识别并路由
- 更明确的角色 / 目标推荐
- 会话间上下文流转更自然
- 人类能够看到“谁在调谁、为什么调”

### 产品价值

这一版意味着 LunaAgentOS 开始真正长出自己的协作语义层，而不只是做入口聚合。

### 关键前提

要让人类或 agent 知道“该把内容发给谁”，系统需要开始具备最小的目标认知：

- 每个入口是谁
- 它适合做什么
- 它当前是否可用
- 它当前有哪些活跃 session

所以 `Stage 2` 的难点不是“多几个 agent”，而是“目标寻址与角色认知”。

## Stage 4：控制平面雏形

### 目标

从工作台升级到控制层。

### 核心能力

- provider 管理器
- agent 生命周期管理
- 会话恢复
- 人类审批流
- 任务分发
- 归档与回放
- 多 runtime 编排
- 更完整的状态观测

### 产品价值

这一版对应的是最初的方向：

LunaAgentOS 开始长成异构 Agent 之上的控制平面，而不是单纯桌面入口。

## 当前执行建议

如果只看最近一段时间的节奏，建议严格按这个顺序推进：

1. 先做完 `v1`
2. 再做 `Stage 2` 的调用流
3. 再碰更完整协作工作台
4. 最后才碰更完整的控制平面

一句话总结：

**先拿到异构入口价值，再拿到调用流价值，再拿到协作工作台价值，最后才拿到控制平面价值。**
