# 第一版交互模型

## 核心目标

第一版不是完整的多 Agent 编排平台，而是一个已经能承接真实主入口的桌面控制台。

当前阶段先稳住一条主链路：

1. 启动控制台
2. 左侧展示 provider 与 agent 舰队
3. 右侧展示历史任务
4. 用户设定主 agent
5. 用户输入任务并发送给主 agent
6. 中间工作台生成该 agent 的会话卡片
7. 卡片承载输出流、思考流与最终响应
8. 会话结果写入按日期归档的历史 JSON

## 三区职责

### 左侧：舰队与配置区

左侧不是工作区切换器，而是 provider / agent 的展示区与配置区。

当前职责：

- 展示有哪些 provider
- 展示每个 provider 下有哪些 agent
- 设定谁是当前主 agent
- 预留 provider 管理按钮
- 预留新增 agent 按钮

当前阶段左侧点击 agent 不承担切换主区的职责。

### 中间：会话工作台

中间区域是工作台，不是单会话详情页。

工作方式：

- 启动时可以为空
- 只有在用户把任务发送给主 agent 后，第一张 agent 会话卡片才入场
- 后续每发起一个主 agent 会话，就新增一张卡片

每张卡片的核心内容是：

- 输出流
- 思考流
- 最终响应

卡片顶部只保留轻量标题信息：

- agent 名称
- 当前状态
- 当前任务

交互要求：

- 每张卡片有独立滚动条
- 每张卡片支持全屏
- 当前阶段优先实现入场机制
- 退出 / 折叠 / 回收只记录需求，不在第一版实现

### 右侧：历史任务

右侧优先做历史任务区，而不是复杂监控系统。

当前职责：

- 展示历史任务
- 按日期分组
- 从本地 JSON 读取
- 作为后续恢复会话与回放的基础

## 主 agent 机制

第一版必须显式定义主 agent。

原因不是产品装饰，而是：

- 用户输入默认要发给谁，必须先有定义
- 第一版不处理复杂调用流
- 其它 agent 的唤起以后再通过调用流设计进入

因此当前规则是：

- 输入框任务默认只发给主 agent
- `发送` 与 `发给主 Agent` 都只作用于当前主 agent
- 主 agent 设定结果需要持久化

## 启动行为

启动时不做复杂自动操作。

当前只做两件事：

1. 展示已有 provider 与 agent 舰队
2. 后台读取并展示历史任务

当前阶段明确不做：

- 启动时自动拉起真实 Claude CLI
- 启动时自动探测并打开会话
- 启动时自动生成 agent 卡片

这样做的目标是让 UI 秒开，并把重操作留给显式用户动作。

补充约束：

- 首屏优先渲染静态工作台，再异步补齐历史任务
- 启动时不允许弹出 CLI 命令窗口
- 运行时探测只由显式按钮触发

## 按钮语义

### 刷新状态

只负责刷新 provider / agent 的运行时可用性。

当前不应该：

- 重开现有会话
- 自动刷新主工作台内容
- 自动触发 Claude 会话探测
- 阻塞首屏或打断正在进行中的会话

### 发送

是第一版的核心动作。

行为：

1. 把输入任务发送给主 agent
2. 在中间工作台创建一张新的会话卡片
3. 先让卡片入场，再在后台等待运行时返回内容
4. 将任务摘要写入历史 JSON

### 发给主 Agent

当前阶段与 `发送` 等价，属于顶部快捷入口。

后续如果需要，可以再区分成：

- 快捷发起新会话
- 执行预置任务

## 历史任务 JSON

第一版不引入复杂数据库，先用按日期的 JSON 文件持久化。

最低字段：

- `id`
- `date`
- `created_at`
- `provider_id`
- `provider_name`
- `agent_id`
- `agent_name`
- `task`
- `status`
- `summary`

后续再考虑扩展：

- 完整事件流
- 工作目录
- 结果附件索引
- 重新打开会话的恢复信息

## 第一版明确不做

- 复杂多 Agent 调度
- 调用流编排
- 退出机制
- 卡片自动折叠与归档动画
- 独立工具面板
- 启动即自动重探测真实 CLI
- 点击左侧 agent 就刷新主区

## 当前价值

如果这条主链路跑通，第一版已经具备最初产品价值：

- 用户不必直接进入 Claude CLI
- 可以在 LunaAgentOS 中定义主入口
- 可以在桌面工作台中发起多会话
- 每个会话以卡片形式留在工作台
- 历史任务可被沉淀与回看

这意味着第一版已经开始替代 CLI 的使用入口，而不只是做一个协议演示器。
